# What twes-in needs from phorj

> Hand this to phorj. Every row is **measured against phorj's tree at `1.0.0-nightly.0`, commit `b9e74cd`
> (2026-08-06)** — its `docs/EXTENSIONS.md` (which is generated by `phg extensions --docs`, so it is the
> authoritative inventory), its `Cargo.toml` feature flags, and the Rust sources of the extensions that matter
> here. Nothing below is recalled.
>
> Four sections: **EXISTS** (don't build it twice) · **MUST BUILD** (8 items, priority-ordered) ·
> **MUST CONFIRM** (6 questions where the answer changes what twes-in can do) · **WON'T ASK FOR** (things a
> reader would expect to see here and shouldn't). Names are proposals; **semantics are the requirement**.
>
> Paths like `src/ext/database/natives/postgres.rs` and `DEC-208` are **phorj's**, cited as evidence — not
> pointers a twes-in session should follow. Only twes-in's own `CLAUDE.md` is authority here.

## Read this first: twes-in is NOT waiting on any of it

`VISION.md` is explicit and this document does not soften it: *"A future rewrite of the core in phorj is
**vision, not a target**: the language is unfinished and nothing here is built for it. Do not treat it as a
requirement, do not design around its unknowns, and do not defer a decision waiting for it."*

So this is a **wish-list addressed outward**, not a roadmap twes-in has adopted. Two consequences worth stating
because they change how the list should be read:

- **Nothing here is a phorj bug.** Every gap is "twes-in would need X"; phorj is a general-purpose language and
  owes an invoicing product nothing. Several items (PDF, XAdES) are things most languages leave to libraries.
- **The list is dominated by what an INVOICING product needs, not by what a web app needs.** phorj's web-app
  story is already strong (see EXISTS). What is missing is almost entirely the *document* and *compliance*
  half — which is also the half that is legally load-bearing, and therefore the half where a workaround is not
  acceptable.

**Why the list is short in the places that matter most.** twes-in's crown-jewel decision is that money is an
exact decimal, never a float (`CLAUDE.md` § Gotchas, day zero, recorded as unfixable-later). phorj's `decimal`
is **fixed-point `i128` with a `u8` scale**, and an alignment that leaves `i128` range **faults** rather than
wrapping [Verified: `src/value/decimal.rs:1-30`, `dec_align`/`dec_scale_up` return `None` on
`checked_pow`/`checked_mul` overflow]. That is stricter than twes-in's own `bcmath`-over-strings implementation
and removes the single largest risk of a port. **The foundation is right; the periphery is what is missing.**

## ❌ MUST BUILD

### ① PostgreSQL over TLS. **Blocks every deployment that is not same-host** — and it is small

```rust
// src/ext/database/natives/postgres.rs:32,98
use postgres::{Config, NoTls};
let client = config.connect(NoTls).map_err(|e| { … });
```

`NoTls` is not a default here — it is the **only** path. There is no TLS type parameter anywhere in the module
[Verified: `grep -n "NoTls\|MakeTlsConnect\|Tls" src/ext/database/natives/postgres.rs` → two hits, both the
above].

**Why this is item 1 despite being the smallest of the large ones:** a managed PostgreSQL (RDS, Cloud SQL,
Neon, Supabase, Scaleway, OVH) refuses or strongly discourages an unencrypted connection, and several reject it
outright. So a phorj application today can only reach a database on `localhost` or across a trusted private
network. For twes-in that is disqualifying rather than inconvenient: it handles invoices, client names,
addresses and payment references, which is personal data under the GDPR — and twes-in's own `CLAUDE.md` treats
a PII exposure as a reportable-breach-class defect. Sending it across a network in the clear is not a trade the
product can make.

**Requirements:**

1. **TLS available, and `sslmode` honoured from the DSN** — `require`, `verify-ca`, `verify-full` at minimum.
   The `postgres` crate supports this through `postgres-rustls` or `postgres-native-tls`; phorj already depends
   on rustls for `Core.HttpClient`, so **rustls is the consistent choice** and adds no new trust store.
2. **`verify-full` must actually verify the hostname**, not just the chain. A TLS implementation that encrypts
   without authenticating is worse than none, because it *looks* solved.
3. **A refused or failed TLS handshake is `ConnectionError`, distinguishable from an auth failure.** twes-in's
   experience is specific here: a `password authentication failed` and a refused connection sent a reader
   hunting for the wrong cause, and the fix was to make the message name the real one.
4. **Do not make TLS opt-in at the DSN level only.** Ideally a build or config setting can make plaintext
   *refuse* — the same shape as `Core.Mail`'s TLS-or-refuse (`DEC-265`), which phorj already got right for
   SMTP. Consistency with your own mail decision is the argument.

### ② Native `NUMERIC` ↔ `decimal`, both directions. **Blocks the money foundation**

phorj's own module documentation states the current position:

> *"the common scalar set (bool, int2/4/8, float4/8, text family, bytea) is native, and richer types (numeric,
> json, timestamp, arrays) are read via a `::text` cast (a clear DatabaseError guides the caller) — matching
> slice E's 'store decimal columns as TEXT' guidance"*
> — `src/ext/database/natives/postgres.rs:12-14`

**The `::text` read is a workaround twes-in can live with. The "store decimal columns as TEXT" guidance is
not**, and the distinction is the whole item:

- A `TEXT` column **cannot carry a scale**. twes-in's money columns are `NUMERIC(19,4)` and its quantity
  columns `NUMERIC(21,6)`; the scale is a *constraint the database enforces*, and it is what makes a
  three-decimal currency exact. The default currency is **TND**, which has **three** decimal places — so a
  two-decimal assumption is a bug for the *default* currency, not an edge case, and Tunisia's stamp duty of
  `0.100 TND` must represent exactly.
- A `TEXT` column **cannot be summed, ordered or range-checked by the server**. Every report, every ledger
  total, every `CHECK (amount >= 0)` moves into application code — which is precisely where a billing system
  must not put arithmetic it can have the database guarantee.
- A `TEXT` column **admits `'abc'`**. `NUMERIC` does not.

**Requirements:**

1. **Bind a `decimal` to a `NUMERIC` parameter natively**, preserving unscaled value and scale — no
   round-trip through a formatted string, because that is where a scale silently changes.
2. **Read a `NUMERIC` column into a `decimal` natively**, preserving the column's declared scale. Note this is
   the direction that matters for correctness rather than convenience: PostgreSQL returns `NUMERIC(21,6)` as
   `2.000000` for a stored `2`, and a consumer needs to know that is the same *number* at a *different scale*
   — which a typed decimal expresses and a string does not.
3. **`NUMERIC` out of `i128` range must FAULT, not truncate.** PostgreSQL `NUMERIC` is arbitrary-precision and
   `decimal` is `i128`, so the ranges genuinely differ. A loud fault is right; a silent narrowing near money is
   the defect this whole item exists to prevent.
4. **Retire the "store decimals as TEXT" guidance for the Postgres driver** once 1–3 land. Guidance outlives
   the constraint that produced it, and this one steers new code into an unfixable shape.

**Also in scope if cheap: `timestamptz`.** Same argument in a smaller way — an invoice date is a legal fact,
and a `TEXT` timestamp cannot be compared or indexed as a time.

### ③ `RoundingMode.Unnecessary`. **Tiny, and it is how a money type says "this must be exact"**

phorj has seven variants; twes-in has eight. The eighth is not a rounding mode — it is an **assertion that no
rounding is required**, which faults if rounding would occur. Java spells it `RoundingMode.UNNECESSARY`.

**Why it earns a line in a language:** it turns a class of bug into a fault at the point of the operation.
`total.divide(count, RoundingMode.Unnecessary)` says *I believe this divides exactly, and I want to know
immediately if it does not* — which is the only safe way to write an allocation, a split, or a proportional
charge. Without it the alternative is to divide with some mode and then compare the result back, which is three
lines instead of one and which people skip.

Effort is a variant plus a fault path in `round_div`.

### ④ A CSPRNG. **`randomBytes(n)` — small, and there is no exposed one today**

Randomness exists inside phorj, in `src/ext/session/natives.rs`, for session-id generation. There is **no
`Core.Random`, no `randomBytes`, no `randomInt` in the language surface** [Verified: a grep for those symbols
across `src/` returns only that one file, and `docs/EXTENSIONS.md` lists no such extension].

twes-in needs cryptographically strong bytes in two places, and both are security-critical:

1. **The unauthenticated client portal's token.** twes-in has a standing ruling — recorded in `CLAUDE.md`
   § Gotchas after a certification round measured it — that a **UUIDv7 identifier is an ordering artefact,
   never a secret**: its random field is *incremented* rather than redrawn between same-millisecond siblings,
   and the generator's seed is recoverable from the output. So the portal gets its own `random_bytes(32)`
   token, never the document primary key. That ruling needs a primitive to stand on.
2. **Identifier generation.** See the note under Q3.

**Requirements:** a CSPRNG (`getrandom`, i.e. the OS source), `randomBytes(n): bytes` and
`randomInt(min, max)` with **no modulo bias**, and — the part worth being explicit about — **no seeding API**.
A seedable "secure" generator is how a CSPRNG becomes a PRNG in someone's test helper and then in production.
If a deterministic generator is wanted for tests, give it a different name and a different type, the way
`Time.freeze` is separate from `Instant.now`.

### ⑤ PDF generation. **Blocks the entire document deliverable**

An invoice **is** a PDF. Not primarily — legally. It is what the client receives, what the accountant files and
what a tax authority audits, and twes-in's guarantee is that re-downloading an issued document is
**byte-identical forever** (which is why the rendered document number is a persisted column rather than
recomputed). There is no PDF anywhere in phorj [Verified: no `Core.Pdf`, no PDF row in `docs/EXTENSIONS.md`].

**This is the largest item and it is also the one most reasonably answered with "not in the language".** So the
requirement is deliberately framed as a choice, cheapest first:

**Option A — nothing, because `Core.HttpClient` is already enough (recommended).** phorj has `Core.Html` for
building the markup and `Core.HttpClient` for POSTing it to a renderer. twes-in's current stack already renders
through **Gotenberg** over HTTP, in its own container — so a phorj port could do exactly the same thing today
with no new language feature at all, provided Q4's answer covers receiving a binary response body.

That makes item ⑤ **much smaller than its position in the table suggests**, and the honest summary is: *the
recommended option needs nothing built.* What it needs is the two supporting answers — a binary/streamed
response (Q4) and Arabic shaping, which is the renderer's problem rather than phorj's.

**A process-spawn primitive would be the alternative, and there is none.** Worth stating precisely because the
symbols mislead: `spawn` is a **language keyword** for concurrency (`src/parser/mod.rs:264`,
`src/lsp/keywords.rs:56`), and `exec` is a **`Core.Database` native** (`src/ext/database/natives/registry.rs:121`)
— neither runs a subprocess. So `weasyprint` and `chromium --headless` are not reachable, only network
renderers are. That is a real constraint but not a blocking one, and it is **not** worth building process spawn
just for PDF: the HTTP route is better isolated anyway, which is why twes-in chose it.

**Option B — `Core.Pdf`, a real generator.** Text, fonts with embedding, images, tables, page breaks,
PDF/A-3 conformance. That last one is not optional for Factur-X: it requires PDF/A-3 with the XML as an
embedded file, and a PDF library that cannot do PDF/A-3 does not solve the compliance problem even though it
produces a PDF. Large, and honestly probably not a language's job.

**Either way, the hard requirements are:** deterministic output for identical input (no embedded timestamp or
random document ID, or a way to fix them), **font embedding** — because a document must render identically on a
machine that lacks the font — and **Arabic shaping and right-to-left layout**, which is where most PDF
toolchains quietly fail and which twes-in cannot skip because `ar` is a first-class locale.

### ⑥ XML — parse, render, namespaces. **Blocks EN 16931, UBL, CII, Factur-X, Peppol**

There is no XML in phorj [Verified: no `Core.Xml`, no row in `docs/EXTENSIONS.md`]. `Core.Json` and `Core.Csv`
exist; XML does not.

European e-invoicing is XML and is not negotiable: **EN 16931** is the semantic standard, with **UBL 2.1** and
**UN/CEFACT CII** as the two permitted syntaxes, **Factur-X/ZUGFeRD** as the hybrid PDF+XML form, and **Peppol
BIS** as the network profile. France's mandate makes this a legal requirement rather than a feature, and it is
arriving across the EU. A billing product that cannot emit a valid UBL or CII document cannot be sold in Europe.

**Requirements, in the order that matters:**

1. **Namespace-correct rendering.** UBL uses several namespaces at once (`cbc:`, `cac:`, `ubl:`) and a
   validator rejects a document whose prefixes or declarations are wrong. A string-templating approach — which
   is what a language without XML forces — produces documents that look right and fail validation, which is the
   worst failure mode because it is discovered by the customer's tax authority.
2. **Parsing with the same fidelity**, for inbound invoices — receiving is half of Peppol.
3. **XSD schema validation**, or at least a documented way to reach one. This is how you find out the document
   is wrong *before* sending it.
4. **Canonicalisation (C14N).** Not a nice-to-have: it is a prerequisite for item 7, because a signature is
   over the canonical form. Building XML without C14N means item 7 cannot be built at all later.
5. **XXE refused by default.** An inbound-invoice parser is an attacker-facing surface; external entity
   expansion is the classic hole. This should be a default, not an option — the same "safe by construction"
   posture phorj already took for DSN password redaction.

---

### ⑦ XML digital signatures (XAdES). **Blocks compliance, not just format**

Several jurisdictions require an invoice to be *signed*, not merely well-formed. XAdES-B/-T over the XML
document is the mechanism, and it needs canonicalisation (item 6.4), X.509 certificate and private-key
handling, and a timestamp-authority round trip for `-T`.

Large, specialised, and the item most defensibly answered "use a library". Listed because **the order matters**:
if item 6 ships without C14N, item 7 becomes a rewrite of item 6 rather than an addition to it. That is the only
thing this entry is really asking for — that item 6 be built with item 7 in mind.

### ⑧ i18n — message catalogues, plural rules, RTL. **`fr` / `en` / `ar`, and Arabic is first-class**

twes-in ships three locales and has already made two rulings this touches:

- **A refusal message is the only instruction a user gets**, so a missing key must not render as the raw key.
  twes-in's own experience: without a translator fallback, an Arabic-speaking user would have been shown
  `document.quantity_too_precise` as their entire error message.
- **A placeholder carrying an enum takes a translated LABEL, never the backed value.** Interpolating a wire
  value into a French sentence renders *"Ce document est issued"*. And the label must be *grammatically*
  hostable: twes-in split one key into two rather than interpolate a noun, because `line` and `fixed charge`
  are gendered and pluralised differently in French and Arabic (`une ligne` / `un frais`), so no single sentence
  can host either in any language.

**Requirements:** a catalogue format with a locale fallback chain; **CLDR plural categories** (Arabic uses
*zero, one, two, few, many, other* — six, where English uses two, so a naive `count == 1 ? a : b` is wrong in
Arabic and there is no way to spell it correctly without the rules); parameter interpolation that a translator
can reorder; and **RTL** support that reaches the *rendered document* (see item 5), not only the UI.

Not asked for: full ICU MessageFormat. The plural categories are the part that cannot be worked around.

## ❓ MUST CONFIRM — the answer changes what twes-in can do

### Q1 — Can `Core.Database` execute `set_config('twes.tenant_id', $1, true)` and read `current_setting()`? **This is the entire tenancy design**

twes-in is multi-tenant and its isolation is **PostgreSQL row-level security**, not application filtering. The
ruling is recorded and the reasoning is short: a query filter is opt-in per query, and a native query, a raw
fragment, a migration, a reporting job or a `psql` session all bypass it — whereas an RLS policy is applied by
the server to every statement whatever issued it. Forgetting must be *impossible*, not merely discouraged.

The mechanism is a **transaction-local** session variable:

```sql
SELECT set_config('twes.tenant_id', $1, true);   -- `true` = transaction-local, NOT session
-- every policy then reads: current_setting('twes.tenant_id', true)
```

Transaction-local matters: a session-scoped value **leaks to whoever gets the connection next**. And the policy
compares against `current_setting(…, true)`, which is NULL when unset — so an unbound session sees **nothing
rather than everything**, and that fail-closed direction is the whole design.

This is probably just "yes, it is a statement with a bound parameter". It is Q1 rather than assumed because if
the driver normalises, pools, or resets sessions in a way that discards a transaction-local `set_config`, the
isolation model does not work at all and nothing else on this list matters.

**Two follow-ups, both needed for the same design:**

- **Is a connection's session state reset between uses, and can application code hook that?** twes-in issues
  `DISCARD ALL` when a connection is released, because a temporary table, a `CURSOR WITH HOLD` and a `LISTEN`
  registration all **outlive a transaction** and are readable under whatever tenant is bound next. Note
  `pg_temp` precedes `public` in the search path, so a temporary table named after a policed one intercepts
  every unqualified reference to it — the leak arrives under the real table's own name.
- **Can application code assert the connecting role's attributes?** twes-in refuses to run if its runtime role
  is `SUPERUSER` or has `BYPASSRLS` (both make RLS inert), owns the policed tables (an owner can
  `ALTER TABLE … DISABLE ROW LEVEL SECURITY`, and `FORCE` does not prevent *removing* a policy, only
  *skipping* it), or holds `TRUNCATE` (never subject to row security at any privilege level). These are
  `pg_roles` / `pg_class` reads — so the question is only whether they are reachable.

### Q2 — Is a `SAVEPOINT` **observable** to application code?

phorj nests transactions with `SAVEPOINT` (`DEC-340`), which is the same choice DBAL made — and twes-in
reproduced a **cross-tenant read** through it, on a real connection with no ORM involved:

`ROLLBACK TO SAVEPOINT` restores transaction-local settings to their value at the savepoint. So a tenant
binding made *inside* a savepoint is silently reverted, while the application still believes the new tenant, and
every subsequent statement is scoped to the *previous* tenant under the *new* tenant's name. Every isolation
test passed throughout, because none of them crossed a savepoint.

twes-in's remedy is a re-check driven from the seam that **emits** the savepoint — not from each caller —
because the nesting is issued by the framework, so the code that *creates* the divergence need not contain the
word "savepoint" and its author has no cue to check.

**So the question is: can a phorj program observe or hook savepoint operations?** A middleware seam, an event,
or a documented way to run code after a savepoint rollback. If the answer is no, a phorj port of twes-in has a
known cross-tenant read with no available fix, and that is worth knowing before anyone starts.

Two smaller facts twes-in measured that may save you the experiments: **`RELEASE SAVEPOINT` does not revert a
transaction-local setting** (only `ROLLBACK TO` does), and PostgreSQL accepts **four** spellings of a savepoint
rollback with the `SAVEPOINT` keyword **optional** — `ROLLBACK TO sp1`, `ROLLBACK TRANSACTION TO SAVEPOINT sp2`,
`ROLLBACK WORK TO SAVEPOINT sp3`, plus the canonical form. Matching on a literal string misses three of them.

### Q3 — Is the `uuid` column type bindable and readable natively?

Every twes-in primary key is a `uuid` column. `uuid` is not in the driver's documented native scalar set
(bool, int2/4/8, float4/8, text family, bytea), so it presumably falls to the `::text` cast. That is *workable*
— a UUID is a string in the application either way — but it means every key comparison, join and `IN` clause
needs a cast, which is easy to forget in one place out of twenty.

**And a related gap:** twes-in generates **UUIDv7** identifiers, for the ordering property. There is no UUID
generation in phorj, and item ④ (a CSPRNG) is a prerequisite for writing one. If a `Core.Uuid` is ever
considered, one warning from twes-in's own measurements, which cost a certification round to establish: a v7
identifier's random field is typically **incremented** rather than redrawn between same-millisecond siblings,
its seed is recoverable from a handful of outputs, and it is therefore **an ordering artefact and never a
secret**. Document that in the module rather than letting each consumer discover it.

### Q4 — Can `Core.Http` stream a response body?

An invoice PDF is small; a year's export is not. If a response body must be fully materialised in memory before
sending, a large document download becomes a memory ceiling. Related: can a response set
`Content-Disposition` and a binary `Content-Type`, and is there a sane way to serve bytes rather than text?

### Q5 — Is there a schema-migration story, or is it entirely ours?

There is no migrations facility in phorj [Verified: a grep for "migration" across `src/` and
`docs/EXTENSIONS.md` returns only unrelated hits — parser tests and a `rewrite_new` CLI]. That may well be the
right scope decision; the question is whether one is planned, because it changes an estimate rather than a
possibility.

Worth knowing either way, because it is the part a migration framework does *not* solve: twes-in's migrations
are **hand-written rather than diff-generated**, and deliberately. A diff produces the `CREATE TABLE`
statements and nothing else — it cannot know about row-level security, and a tenant-owned table without a policy
is completely unpoliced while looking finished. So the RLS statements are issued by the migration itself and a
separate gate checks a *live* schema for them. Any migration tool phorj grows will have the same blind spot;
that is not a criticism of the tool, it is the reason the gate exists.

### Q6 — Is `statement_timeout`, or a per-query deadline, settable?

twes-in's document numbers are **gapless** — a legal requirement, since a missing invoice number is what a tax
authority reads as a suppressed sale. That rules out a PostgreSQL `SEQUENCE`, which is deliberately
non-transactional and does not roll back, so every failed issue would burn a number. The shape that satisfies
the contract is a per-`(tenant, type)` counter row taken under `SELECT … FOR UPDATE` inside the same transaction
that persists the document.

The accepted cost is that issues for one `(tenant, type)` **serialise**. That is correct — two invoices sharing
a number is worse than a queued request — but it means a lock can be waited on, and a bounded wait that fails
loudly is much better than an unbounded one. `TimeoutError` already exists in the taxonomy and is mapped from
SQLSTATE `57014` (`query_canceled`, i.e. a fired `statement_timeout`), which suggests the answer is yes and the
question is only how it is set.

## 🚫 WON'T ASK FOR — and why, so nobody builds it for us

| Thing a reader might expect here | Why it is not asked for |
|---|---|
| An ORM | twes-in deliberately **does not use its ORM's unit of work** for writes. The aggregate is immutable, so there is no dirty state to diff, and a whole-rewrite of child rows through an identity map is *impossible* rather than slow — it raises an identity collision before any SQL is emitted. So a repository over bound SQL is the target shape, and `Core.Database` already provides it. **Please do not build an ORM on twes-in's account** |
| A dependency-injection container | The domain layer must depend on nothing, which is enforced by a gate. Ports are interfaces and adapters are constructed explicitly. Wiring is a solved problem at this scale |
| A validation framework | Invariants live in the value objects and are enforced in constructors. Edge validation is a message-quality feature, not a correctness one |
| A migration *framework* | See Q5 — a tool cannot know about row-level security, so the gate is needed regardless |
| A process-spawn primitive | **There is none** — `spawn` is a concurrency keyword and `exec` is a `Core.Database` native, so no subprocess route exists [Verified]. Not asked for anyway: the PDF renderer is reachable over HTTP (item ⑤ Option A), which is better isolated than a subprocess and is what twes-in already does. Building process spawn to solve PDF would be the wrong trade |
| A templating engine | `Core.Html`'s builder is better for this than a template language — a document is assembled, not authored |
| An events / message bus | twes-in uses one, but nothing about it needs language support |

## Appendix — what a phorj port would GAIN, not just cost

Stated because a requirements list reads as a list of complaints, and the honest picture is not one-sided. Four
things twes-in currently pays for that phorj would simply remove:

1. **An exact decimal in the kernel.** twes-in's `Money` is built on `bcmath` over decimal strings, with a
   hand-written `applyRounding()` covering all eight modes and tested exhaustively across negative ties —
   because PHP has no exact decimal type. phorj has one, fixed-point `i128`, with faulting overflow. That code
   would be **deleted**, not ported.
2. **The clock port disappears.** twes-in injects a `ClockInterface` because ambient time is untestable in PHP.
   `Time.freeze`/`unfreeze` makes the port unnecessary.
3. **A single binary instead of a runtime.** No PHP-FPM, no FrankenPHP, no extension matrix, no
   `composer install` provenance question.
4. **A SQL-injection lint in the compiler.** twes-in enforces bound parameters by review and by a
   reviewer charter. `W-SQL-INJECTION` enforces it by build.

And one thing that makes the whole idea tractable rather than theoretical: **`phg transpile` is a mandatory
backend, not an optional one.** A phorj port of twes-in would not have to be all-or-nothing, which is the single
biggest risk any rewrite carries.
